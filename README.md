# Eviction Settlement Opportunity Detector — prototype (Team 14)

> **Prototype — synthetic data only. Not legal advice.** Every name, address, phone number, case
> number and outcome in this repository is generated. Court IDs use county numbers that do not
> exist in Indiana, and phone numbers use the 555-01xx range reserved for fiction.

A court-facing tool for Indiana small-claims eviction (EV) cases. It reads the court's daily case
export (simulated here), invites tenants and landlords to answer a short questionnaire through a
private link or QR code, and ranks open cases so court staff can reach the ones most likely to
settle **before the first hearing**, when diversion (mediation, payment plans, agreed move-outs,
rental assistance) is easiest to arrange.

The tool is **advisory only**. Scores set call priority, never eligibility: it never blocks,
delays or decides anything, every case still gets the standard diversion offer, and it never
writes to Odyssey; staff record official events there themselves. Each score comes with 2–4
plain-language reasons. A party's answers are never shown to the other party; the judge and court
staff can see both.

## Quick start

**Docker** (any OS):

```bash
docker compose up
```

Open http://localhost:8000. The first start builds the synthetic data, runs the tests and writes
the reports, which takes 2–3 minutes. Later starts reuse the data volume. To reset, run
`docker compose down -v`.

**Local Python 3.11+:**

```bash
make setup && make seed && make run
```

Without `make` (e.g. on Windows), use the same commands through `manage.py`:

```bash
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt
.venv/Scripts/python manage.py demo
.venv/Scripts/python manage.py run
```

`make demo` (= `python manage.py demo`) does a fresh seed plus tests and every report, which is
everything the demo below needs. `make seed` alone takes about 25 seconds.

<details>

- **"The filename or extension is too long"** when importing compiled packages: the project

  `python -m venv --system-site-packages .venv`, then
  `pip install fastapi uvicorn python-multipart faker "qrcode[pil]" ruff`.

## 5-minute demo script

The case numbers for each step are in `data/demo/demo_cases.json`, regenerated by every seed.
A presenter version with talking points is in [docs/DEMO_SCRIPT.md](docs/DEMO_SCRIPT.md).

1. **Import `day1.csv`.** Sign in as `clerk` → *Import feed* → **Import day1.csv**. The report
   shows new and updated cases, 3 rejected rows with reasons (bad case number, wrong case type,
   defendant count mismatch) and any reconciliation flags.
2. **Open a tenant QR link on a phone and submit the intake.** Open the case
   `day1_new_filing_for_qr_demo` from the queue. Scan the tenant's QR code with a phone (set
   `PUBLIC_BASE_URL` to this computer's LAN address first) or open the link. The disclosure comes
   first; try *Español*; answer and submit, and tick "Repairs" to see the legal-aid flag.
3. **Watch the dashboard update.** Back in the queue, the case now shows tenant "Yes", a
   settlement potential, pathway, the **Legal-aid referral** flag, consent and the next action.
4. **Import `day2.csv`.** *Import feed* → **Import day2.csv**. It contains a continuance, a
   dismissal, a diversion stay and a newly sealed case. The queue re-sorts, the dismissed case
   leaves the call list, and the reconciliation table lists cases staff were working that the feed
   has now decided.
5. **Mark a diversion agreement and show the checklist.** Sign in as `facilitator`, open
   `diversion_agreement_candidate` → **Both agreed to diversion**. The tool shows the Odyssey
   checklist and a draft order with the 30- and 60-day dates, both marked DRAFT; nothing is sent
   anywhere. The `day2_diversion_stay` case shows *In diversion* with its check dates and a
   Restricted badge.
6. **Show that the sealed case disappears from the clerk view.** As `clerk`, search the queue
   for `day2_newly_sealed`: it is gone (its URL returns 404). As `facilitator` it is still there,
   badged *Restricted*, and opening it is written to the audit log (admin → *Audit log*).
7. **Open `reports/summary.md`** (or admin → *Reports*): recall held at ≥ 0.95, the false
   positive learning curve, expert agreement and median intake time.

## Tests and evaluation commands

| Command | What it does | Output |
|---|---|---|
| `make test` | pytest: the 16 section-G scenarios plus unit, web and guard tests | `reports/test_results.xml` |
| `make lint` | `ruff check` + `ruff format --check` | — |
| `make eval-model` | time split; threshold for recall ≥ 0.95 on validation; AUC, calibration, staircase; recall/FPR/precision with bootstrap CIs | `reports/model_eval.md` + PNGs |
| `make eval-learning` | 12-week feed with weekly retraining, fixed holdout, champion–challenger log, FPR vs. training size, exploration sample | `reports/learning.md`, `champion_log.csv` |
| `make expert-pack` | 50 blind scenarios stratified by tier and pathway | `reports/expert_pack/packet.html`, `ratings.csv` |
| `make expert-compare RATINGS=ratings.csv` | Spearman, top-tier overlap, 10 largest disagreements | `reports/expert_compare.md` |
| `make usability` | median intake time from recorded timestamps (real and seeded reported separately) | `reports/usability.md` |
| `make summary` | one-page summary of everything above | `reports/summary.md` |
| `make eval-all` | all evaluations, then the summary | — |
| `make purge [DAYS=90]` | delete intake details N days after closure, keep aggregate counts | console + audit log |
| `make import FILE=path.csv` | import an export from the command line | console |

Without real expert ratings, `expert-compare` uses `ratings_simulated.csv`, which is labelled
SIMULATED everywhere it appears. During the testing window, have experts fill in
`reports/expert_pack/ratings.csv` and run `make expert-compare RATINGS=reports/expert_pack/ratings.csv`.

## Deployment notes

The image runs on any container host (`docker build .`). One process serves everything on
`$PORT` (default 8000), and SQLite lives in `/app/data` (mount a volume or disk there). The
container starts as root only to make that folder writable, then runs as `appuser` (uid 1000).

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `SECRET_KEY` | **yes** outside a laptop demo | dev value | signs staff session cookies |
| `PUBLIC_BASE_URL` | yes, for QR codes | `RENDER_EXTERNAL_URL` on Render, else `http://localhost:8000` | the address QR codes and party links point to |
| `DATABASE_URL` | no | `sqlite:///data/app.db` | SQLAlchemy URL |
| `APP_TODAY` | no | real date | freeze "today" (YYYY-MM-DD) for a reproducible demo |
| `SEED_ON_START` | no | `true` | Docker: build demo data on first start |
| `DATA_DIR`, `REPORTS_DIR` | no | `data/`, `reports/` | where generated files go |

There are no runtime network calls: HTMX is vendored, there are no CDNs or web fonts, and a
Content-Security-Policy restricts pages to their own origin. Put the app behind HTTPS, since
party links carry a bearer token.

### Render

`render.yaml` is a Render Blueprint: in the Render dashboard choose **New → Blueprint**, pick this
repository and apply. It creates one Docker web service on the **free** plan and generates
`SECRET_KEY`.

- The free plan has no persistent disk, so the image is built with `SEED_AT_BUILD=true`: the demo
  data, tests and reports are generated during the build (a few minutes), and the app's date is
  fixed at the build date (`APP_TODAY`, override it in Render if needed).
- The service sleeps after 15 minutes without visits; the next visit takes about a minute to
  wake it. Every wake-up or restart returns to the clean demo, so **anything entered on the site
  (intakes, statuses, imports) is lost**. Run usability sessions on a local copy, or switch to a
  paid plan with a disk (see the comment in `render.yaml`).
- Each push to `main` rebuilds and redeploys, which also refreshes the demo to the new date.

The demo passwords above are public, so anyone with the URL can sign in. Share the address only
with the team.

## Limitations and next steps

- **Synthetic data only.** Reported metrics show the system works as designed and that the
  learning mechanism behaves as intended. They say nothing about real-world accuracy. The outcome
  mix and effect sizes are placeholders; replace them with Indiana's published *Methods of
  Disposition* shares for EV cases.
- **Court procedure placeholders** (PLAN.md §14B): Odyssey checklist and order text,
  dismissal-to-status mapping, calendar vs. court days, retention period, restriction trigger,
  and use of sealed cases in aggregate training. All of these need court confirmation.
- **Recall ≥ 0.95 makes the High tier broad** (most cases). The false positive rate is the cost;
  the learning report shows how it moves with more data.
- **Layer 2 weights are hand-set.** Once pilot intake data exists, fit them from outcomes.
- **Prototype security:** tokens are stored in plain text so letters can be reprinted. Production
  should hash tokens, add rate limiting to `/find`, use real identity management, and move to a
  managed database.
- **Next steps:** (1) obtain a real historical Odyssey export and re-run `eval-model`; (2) run a
  **silent pilot**: score live cases without acting on them, then compare with recorded outcomes;
  (3) usability sessions with tenants and landlords (median time is in `usability.md`); (4) expert
  ratings with the packet; (5) translator review of the Spanish text.
